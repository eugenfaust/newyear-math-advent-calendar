# Контракт REST API v1

Базовый путь: `/api/v1`. Symfony отвечает JSON в UTF-8. Next.js обращается к нему из серверного окружения по `INTERNAL_API_URL`; браузерские запросы к данным проходят через same-origin обработчики Next.js.

## Формат

- Публичные идентификаторы в URL и JSON — UUID в каноническом текстовом формате. Внутренние числовые ID не передаются клиенту. День (`1…31`) и год (`YYYY`) — числа, не UUID.
- Время хранится в PostgreSQL как `timestamptz` в UTC. API возвращает ISO 8601 с явным смещением, предпочтительно `Z`, например `2026-12-01T00:00:00Z`. Даты без времени — `YYYY-MM-DD`.
- Для POST/PATCH/PUT клиент отправляет `Content-Type: application/json`; успешное создание возвращает `201`, обновление — `200` с ресурсом, удаление — `204` без тела.
- Ошибка имеет вид `{ "code": "STABLE_CODE", "message": "Human-readable text" }`. Код стабилен и машинно читаем, текст может меняться. Неожиданная ошибка получает `INTERNAL_ERROR` и HTTP 500; подробности остаются в серверном журнале. Ошибки валидации получают HTTP 422 и могут дополнительно содержать `details: [{field, message}]`.
- `401 UNAUTHENTICATED` означает отсутствие или истечение удостоверения, `403 ACCESS_DENIED` — недостаточные права. Доменные коды из ТЗ используются с соответствующим HTTP статусом. Ответы с пользовательскими данными помечаются `Cache-Control: no-store`.
- Списки: `?page=1&perPage=20` (страницы от 1, максимум `perPage=100`) и ответ `{ "items": [], "pagination": { "page": 1, "perPage": 20, "total": 0, "totalPages": 0 } }`. Сортировка по явно заданному стабильному полю и UUID как вторичному ключу. Некорректные параметры — HTTP 422.

## Текущий календарь

`GET /api/v1/calendar` выбирает календарь текущего года **по `APP_TIMEZONE=Europe/Moscow` на сервере**. Для MVP действует `UNIQUE(user_id, year)`. Если календарь на этот год не назначен, ответ `404 ADVENT_CALENDAR_NOT_FOUND`, без автоматического выбора прошлогоднего. `GET /api/v1/calendar?year=YYYY` выбирает конкретный год и позволяет посмотреть историю; проверка владельца обязательна. Доступность дня рассчитывается сервером в той же бизнес-зоне; изменение часов браузера ничего не открывает. После 31 декабря незавершённые дни назначенного календаря остаются доступны.

## Аутентификация и граница доверия

Реализация входа и модели User запланирована задачей 02, клиентской оболочки — задачей 03. Их общий контракт:

1. NextAuth v5 Credentials получает `login` и `password` в `authorize()` и серверным запросом вызывает `POST /api/v1/auth/login` с JSON `{login, password}`. Symfony проверяет hash пароля и `isActive`, отвечает `{accessToken, expiresAt, user: {uuid, login, displayName, roles}}`. Ошибка входа — `401 INVALID_CREDENTIALS` без уточнения существования пользователя.
2. Symfony выдаёт случайный непрозрачный bearer token не менее 256 бит. В БД хранится только SHA-256 hash токена, UUID владельца, время выдачи и истечения (UTC), время отзыва. Срок токена и сессии NextAuth — не более 12 часов. Каждый защищённый запрос проверяет hash, срок, отзыв, актуальный `isActive` и роли в БД. Роли из cookie или тела запроса не доверяются.
3. NextAuth использует `session.strategy = "jwt"`, `AUTH_SECRET` и шифрованную HttpOnly cookie с `Secure` в HTTPS и `SameSite=Lax`. Bearer token хранится только во внутреннем JWT NextAuth и извлекается серверным кодом; `session()` отдаёт браузеру только публичные поля пользователя. Серверный API-клиент Next.js посылает `Authorization: Bearer <accessToken>` Symfony. Токен не попадает в `NEXT_PUBLIC_*`, localStorage, HTML или клиентский JSON.
4. Браузер вызывает мутации через same-origin Next.js route handlers. Они проверяют сессию, `Origin` на совпадение с публичным origin приложения и допустимый `Content-Type`, затем передают bearer token Symfony. NextAuth защищает свои операции входа/выхода своим CSRF-механизмом. Symfony повторно проверяет аутентификацию, роль (`ROLE_ADMIN` для `/api/v1/admin/*`), владение ресурсом и доменные ограничения на каждой операции. Bearer API не полагается на cookie, поэтому отдельный CSRF-токен Symfony ему не нужен.
5. Выход вызывает `POST /api/v1/auth/logout` с bearer token, который отзывает текущий token (повторный вызов успешен), затем `signOut()` очищает cookie NextAuth. Даже если cookie или JWT ещё существует, отозванный токен не даёт доступ к API. Деактивация пользователя также прекращает доступ на следующем запросе.

Общедоступный `GET /api/v1/health` проверяет соединение с БД и возвращает `{ "status": "ok" }`; при недоступности БД — HTTP 503 с `{code, message}`. `GET /api/health` на frontend проверяет эту цепочку и имеет такой же статус.

## Администрирование пользователей

Все маршруты `/api/v1/admin/users` требуют действующий bearer token с актуальной ролью `ROLE_ADMIN`. Ответы не кешируются.

- `GET /api/v1/admin/users?page=1&perPage=20&search=...` ищет по имени, логину и email, возвращает стандартный список с пагинацией. Сортировка: дата создания по убыванию, UUID по возрастанию.
- `GET /api/v1/admin/users/{uuid}` возвращает профиль без пароля.
- `POST /api/v1/admin/users` принимает `{login, name, email?, role, isActive?, password}` и возвращает созданный профиль с HTTP 201.
- `PATCH /api/v1/admin/users/{uuid}` принимает любое непустое подмножество этих полей; пароль меняется только при передаче нового значения. Возвращает профиль с HTTP 200.
- `DELETE /api/v1/admin/users/{uuid}` деактивирует пользователя и возвращает HTTP 204. Запись и история сохраняются.

`role` — `ROLE_USER` или `ROLE_ADMIN`, `isActive` — boolean. Логин содержит 1–100 латинских букв, цифр, `_`, `.` или `-` и уникален среди всех пользователей, включая отключённых. Имя — 1–150 символов, пароль — 6–1024 символа. `email` может быть `null`. Ошибки полей — `422 VALIDATION_ERROR` с `details`; занятый логин — `409 LOGIN_TAKEN`; отсутствующий пользователь — `404 USER_NOT_FOUND`.
