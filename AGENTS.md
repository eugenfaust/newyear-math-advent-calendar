# Инструкции для агентов

## Проект и источники требований

Это монорепозиторий математического адвент-календаря: Symfony 7.4 / PHP 8.3+ в `backend/`, Next.js 15 / App Router / strict TypeScript в `frontend/`, PostgreSQL 16. Пользователь получает по одному заданию на каждый день декабря, а за выполнение — игрушку для персональной ёлки с 31 слотом.

Перед реализацией функции прочитайте относящиеся к ней документы:

- `ADVENT_CALENDAR_PROJECT.md` — продуктовое ТЗ; особенно разделы 47 (архитектурные решения), 49 (готовность MVP) и 50 (правила реализации).
- `tasks/README.md` и соответствующий файл `tasks/NN-*.md` — порядок работ, зависимости и критерии приёмки. Номер задачи не означает, что она уже выполнена: сверяйтесь с кодом.
- `docs/api-contract.md` — форматы REST API, аутентификация, ошибки и правила доступа.
- `README.md` — фактический локальный запуск и уже реализованные возможности.

Если документы и код расходятся, выясните причину и согласуйте контракт при изменении обеих сторон. Не меняйте молча решения раздела 47 ТЗ. При изменении поведения обновляйте относящиеся к нему документы и контракт API.

## Структура и локальные команды

- `backend/src/{User,Task,Shared}` — текущие PHP-модули; новые предметные области размещайте аналогично. `backend/migrations/` — миграции Doctrine, `backend/config/` — конфигурация Symfony.
- `frontend/src/app/` — страницы и route handlers App Router; `frontend/src/components/` — общие компоненты; `frontend/src/lib/` — серверный API-клиент и утилиты.
- Для запуска из корня: скопируйте `.env.example` в `.env`, задайте секреты, затем `make init`. После изменения исходников или зависимостей: `make up`; после изменения схемы: `make migrations`; проверка сервисов: `make health`. Другие цели перечислены в `make help`.
- Проверки frontend: `cd frontend && npm run lint`, `cd frontend && npx tsc --noEmit`, `cd frontend && npm run build`. Для PHP проверяйте синтаксис изменённых файлов командой `php -l`; для схемы используйте миграции Doctrine. Тестового скрипта в `package.json` и набора PHPUnit в текущем репозитории нет — не сообщайте о несуществующем прогоне тестов.
- Не добавляйте секреты из `.env` в код, логи или документацию. Не удаляйте Docker-тома `postgres_data` и `uploads` при обычной разработке.

## Архитектурные инварианты

- `AdventTemplate` — повторно используемая конфигурация, `AdventCalendar` — назначенный пользователю календарь. При назначении сохраняйте снимок связей «день → задание»; последующие изменения шаблона не меняют назначенный календарь. Сам текст задания снимок по текущему ТЗ не фиксирует.
- Доступность дней 1–31 вычисляет backend по году календаря и `APP_TIMEZONE` (по умолчанию `Europe/Moscow`). Пропущенные дни остаются доступны, в том числе после декабря. Время хранится в UTC. Не доверяйте часам браузера или frontend-проверкам доступа.
- Завершение задания и выдача игрушки — одна транзакция. Повторное завершение возвращает прежний результат и не выдаёт вторую игрушку. Подкрепляйте инварианты ограничениями БД и тестами на критические сценарии.
- Пользователь может управлять только своими календарями и игрушками. Одна награда соответствует максимум одному выполненному дню; один слот занимает максимум одна игрушка. Backend хранит номер слота, а координаты всех 31 слотов определяются во frontend. Основной способ размещения — нажатие/касание, дерево — SVG + React.
- Для MVP допустим только `answerType=NONE`; не добавляйте автоматическую проверку ответов без отдельного требования. Не раскрывайте `correctAnswer` в пользовательском DTO до выполнения.

## API, безопасность и стиль реализации

- Публичные идентификаторы — UUID; REST API Symfony расположен под `/api/v1`. Соблюдайте коды HTTP, JSON-формат ошибок `{code, message}`, пагинацию и правила времени из `docs/api-contract.md`. Пользовательские ответы должны иметь `Cache-Control: no-store`.
- NextAuth v5 использует Credentials и серверный запрос к Symfony. Bearer token остаётся только в серверной части Next.js; не передавайте его в клиентскую сессию, `NEXT_PUBLIC_*`, localStorage или HTML. Браузерские мутации идут через same-origin route handlers с проверкой сессии, `Origin` и типа содержимого. Symfony на каждом запросе повторно проверяет токен, актуальную роль, владельца ресурса и доменные ограничения.
- Пишите strict TypeScript, избегайте `any`, типизируйте DTO и ответы. Используйте TanStack Query для серверного состояния, Server Components там, где они уместны, и клиентские компоненты для интерактивных сценариев.
- В backend валидируйте входные DTO, держите контроллеры короткими, переносите предметную логику в сервисы. Изменения схемы оформляйте миграциями Doctrine; ограничения БД дополняют прикладную валидацию. Сохраняйте абстракцию хранилища файлов, чтобы заменить `/uploads` без изменения доменной модели.
- Добавляйте зависимости только по конкретной необходимости. Не вводите Three.js, Canvas или WebGL для MVP. При изменении API синхронно обновляйте Symfony endpoint, Next.js route handler/API-клиент, типы и `docs/api-contract.md`.

## Перед завершением работы

Проверьте критерии «Готово, когда» нужной задачи, прогоните относящиеся к изменению проверки и укажите фактический результат. Для изменений в календаре, наградах и ёлке отдельно проверяйте права доступа, повторные запросы и ограничения БД. Не отмечайте задачу завершённой, если её критерии приёмки не выполнены.
