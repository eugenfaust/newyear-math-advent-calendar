# Advent Calendar

Монорепозиторий: Symfony 7.4 / PHP 8.3+ в `backend`, Next.js 15 / App Router / strict TypeScript в `frontend`, PostgreSQL 16. Требования и план: [ТЗ](ADVENT_CALENDAR_PROJECT.md), [задачи](tasks/README.md). Формат API и контракт аутентификации: [docs/api-contract.md](docs/api-contract.md).

## Локальный запуск

Нужны Docker и Docker Compose. Из корня проекта:

```sh
cp .env.example .env
# Замените APP_SECRET, AUTH_SECRET и POSTGRES_PASSWORD случайными значениями.
make init
make create-admin
curl http://localhost:8000/api/v1/health
curl http://localhost:3000/api/health
```

Для генерации секретов можно использовать `openssl rand -hex 32` два раза. Для `POSTGRES_PASSWORD` в локальной конфигурации используйте URL-безопасные символы, поскольку Compose вставляет пароль в `DATABASE_URL` без URL-кодирования. Сайт открыт на http://localhost:3000, backend на http://localhost:8000 (оба порта привязаны к `127.0.0.1`). Результат обоих health-запросов: `{"status":"ok"}`. Команда `app:create-admin` поддерживает два позиционных аргумента: `login` и `password` (`make create-admin LOGIN=admin PASSWORD=...` или `docker compose exec backend php bin/console app:create-admin LOGIN PASSWORD`). Имя пользователя при таком запуске — «Администратор». Цель `make create-admin` сначала обновляет backend-контейнер, затем вызывает команду. Без аргументов команда запрашивает логин, имя и пароль интерактивно. Пароль в аргументе может остаться в истории оболочки и быть виден в списке процессов; для ручного запуска безопаснее интерактивный режим.

PostgreSQL хранит timestamps в UTC. Контейнеры используют UTC; `APP_TIMEZONE=Europe/Moscow` служит только для вычисления даты открытия дней. База хранится в томе `postgres_data`, файлы — в отдельном томе `uploads`, примонтированном к `/uploads` backend. `docker compose down` сохраняет оба тома; `down -v` удаляет их.

После изменения зависимостей или исходников пересоберите образы: `make up`. Логи: `make logs`. Миграции после обновления: `make migrations`. Остальные цели: `make help`.

Если Docker на занятом хосте сообщает `all predefined address pools have been fully subnetted`, создайте локальный `compose.override.yaml` со свободной подсетью для сети `default`. Этот файл игнорируется Git; в текущей рабочей среде использована `10.91.240.0/24`.

Вход доступен на `/login`. После входа пользователь попадает в `/cabinet`, администратор — в `/admin`; главная страница перенаправляет в доступный раздел. Выход находится в шапке. Symfony принимает `POST /api/v1/auth/login` с `{ "login": "...", "password": "..." }`, выдаёт bearer token на 12 часов, а `POST /api/v1/auth/logout` отзывает его. Защищённые запросы передают `Authorization: Bearer <token>`. В админке `/admin/users` доступны поиск, создание, изменение и деактивация пользователей. Деактивация прекращает доступ и сохраняет историю.

API библиотеки заданий: `/api/v1/admin/tasks`. Оно поддерживает создание, редактирование, поиск, фильтры и деактивацию; `POST /api/v1/admin/tasks/{uuid}/image` загружает изображение. Подробности запросов и ограничений: [контракт API](docs/api-contract.md). В админке `/admin/tasks` доступны список, поиск и фильтр по статусу, создание и редактирование с загрузкой изображения. Предпросмотр задания использует общий компонент Markdown и KaTeX для будущей пользовательской страницы дня; HTML из Markdown не обрабатывается.

Библиотека игрушек доступна в админке на `/admin/ornaments`: поиск, создание, редактирование, загрузка SVG/PNG/WebP, предпросмотр и деактивация. Изображения сохраняются в томе `uploads`; неактивные игрушки остаются доступными по прежним URL. Новая игрушка становится активной после успешной загрузки изображения. Формат API описан в [контракте](docs/api-contract.md).

Административный API шаблонов доступен на `/api/v1/admin/templates` и через same-origin `/api/admin/templates`. Он позволяет создавать, редактировать и деактивировать шаблоны, назначать задания на дни 1–31, проверять полноту и атомарно копировать шаблон со всеми связями дней. В админке `/admin/templates` доступны список, создание и редактирование шаблонов: сетка 31 дня, поиск и просмотр активных заданий, замена или очистка дня, проверка готовности и копирование в новый редактируемый шаблон. Подробности DTO и ошибок приведены в [контракте](docs/api-contract.md).

В карточке пользователя `/admin/users/{uuid}` администратор видит историю назначенных календарей и может назначить активный заполненный шаблон на выбранный год. Назначение создаёт 31 день в одной транзакции; повторно назначить календарь на тот же год нельзя. API: `GET` и `POST /api/v1/admin/users/{uuid}/calendars` (через same-origin `/api/admin/users/{uuid}/calendars`). Кнопка «Прогресс и ёлка» показывает 31 статус дня, счётчик и размещённые или ещё не размещённые игрушки. Данные доступны только администратору через `GET /api/v1/admin/users/{uuid}/calendars/{year}/progress`.

Пользовательский API календаря: `GET /api/v1/calendar` возвращает статусы всех 31 дней и счётчики, `GET /api/v1/calendar/days/{day}` — доступное задание. Оба маршрута принимают `?year=YYYY` для истории; без параметра выбирается текущий год по `APP_TIMEZONE`. Закрытый день отвечает `403 ADVENT_DAY_LOCKED`; пропущенные дни доступны и после декабря. Первое успешное открытие фиксирует время. Frontend проксирует чтение через `/api/calendar` и `/api/calendar/days/{day}`. В `/cabinet` показаны прогресс, число игрушек без места и сетка дней; `/cabinet/day/{day}` показывает дату открытия закрытого дня или доступное задание с Markdown, формулами и изображением. Страницы читают API на сервере без кэша.

`POST /api/v1/calendar/days/{day}/complete` завершает доступный день и атомарно выдаёт игрушку; повторный запрос возвращает ту же награду. При отсутствии активных игрушек отвечает `409 NO_ACTIVE_ORNAMENTS` без завершения дня. Браузерский маршрут `/api/calendar/days/{day}/complete` проксирует запрос с проверкой сессии и источника. На странице доступного дня есть кнопка завершения: после ответа показывается выданная игрушка и ссылка на ёлку, а прогресс календаря обновляется.

API ёлки: `GET /api/v1/tree` возвращает выданные игрушки и состояние текущего календаря; `POST /api/v1/tree/ornaments/{uuid}/place` размещает или перемещает свою игрушку в свободный слот 1–31. Оба маршрута поддерживают `?year=YYYY` для истории. Same-origin маршруты frontend находятся под `/api/tree`. Слоты сохраняются в БД; координаты 31 позиции определены во frontend. На `/cabinet/tree` пользователь выбирает игрушку из коллекции или на ёлке и нажимает свободное место для размещения или перемещения. Слоты доступны с клавиатуры и касанием. Появление награды и размещение анимированы; при уменьшении движения анимации отключаются. После 31 выполненного дня API возвращает `completed: true`, и страница ёлки показывает итоговую звезду и поздравление также после перезагрузки.

## Проверка и выпуск

Перед выпуском задайте в `.env` независимые `APP_SECRET`, `AUTH_SECRET` и `POSTGRES_PASSWORD`; `APP_TIMEZONE` определяет дату открытия дней. Compose передаёт Symfony `APP_ENV` и `APP_DEBUG`, а Next.js — серверный `INTERNAL_API_URL`. Не переносите `.env` в репозиторий. Сохраняйте тома `postgres_data` и `uploads` при обновлении: изображения заданий и игрушек находятся в `/uploads` backend и нужны для прежних календарей.

Порядок обновления: сохранить резервную копию базы и тома `uploads`, обновить исходники и переменные окружения, запустить `make up`, затем `make migrations` и `make health`. Первого администратора создайте через `make create-admin` в интерактивном режиме.

Проверки исходников: `cd frontend && npm run lint && npx tsc --noEmit && npm run build`. После миграций в контейнере backend: `php tests/calendar_assignment_smoke.php`, `php tests/calendar_api_smoke.php`, `php tests/completion_rewards_smoke.php`, `php tests/tree_api_smoke.php`, `php tests/release_flow_smoke.php`. Скрипты создают временные записи и очищают их; отдельного PHPUnit-набора пока нет. Для проверки миграций с чистой БД используйте отдельный временный Compose-проект и тома, сохранив рабочие `postgres_data` и `uploads`.
